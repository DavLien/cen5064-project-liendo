# ADR-001: Adopt a 4-Tier Python Architecture with SQLite and JSON for Local Data Storage

**Date:** 2026-10-03
**Status:** Accepted

## Context

The semester timeline and course constraints require GameLedger to be a fully testable system delivered by a solo developer. The application
needs to manage user library states, log play sessions, and read game metadata without introducing heavy external dependencies. Using a live
web API for game catalogs or a client-server database would create setup friction on conference days, where reviewers expect the repository
to run exactly as documented immediately after cloning.

## Decision

GameLedger will be built entirely in Python using a strict 4-tier architecture (Presentation, Service, Domain, Data). The Data tier will utilize
a local SQLite database to persist user progress and an offline `games.json` file as a read-only catalog, both accessed behind a repository
interface so the upper tiers remain isolated from the storage implementation.

## Consequences

Reviewers and instructors can clone and run the system with zero database or API configuration, which protects the project during conference-day
evaluations. The strict architectural boundaries ensure that our core domain logic—such as calculating play hours and updating game statuses—is
highly cohesive and easily covered by standard Python unit tests. We deliberately rule out the use of a live external game database (like IGDB)
or a dedicated server (like PostgreSQL), which trades away distributed systems practice in exchange for guaranteed project completion and reliability.
This decision would be revisited if the dataset grows beyond local storage limits or if multi-user network access becomes a requirement in the future.
